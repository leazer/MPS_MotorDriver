## 2026-06-22 调试串口 finsh 接通 (3 轮调试)

### 背景
Stage 1 硬件 Bring-up 完成后, 接入 RT-Thread finsh/msh 调试控制台, 以便后续 Stage 通过 msh 命令自主闭环验证. 串口硬件: USART1 PB6(TX)/PB7(RX) 115200 8N1, 经 USB-TTL 连接 PC. 用户使用可控电源, 整体安全性可放心调试.

### 第 1 轮: 串口完全无输出

**现象**: 烧录后串口工具收不到任何数据 (完全静默).

**排查过程**:
1. 检查 finsh 配置: `RT_USING_FINSH` (finsh_config.h) 和 `RT_USING_CONSOLE` (rtconfig.h) 两个宏都被注释 → finsh 组件和 console 后端不编译.
2. 检查 USART1 硬件: `wk_usart1_init` 已在 Stage 0 Task 7 清空, platform 层 `board_init_at32m412.c` 未补 USART1 初始化 → 串口硬件未配置.
3. 检查引脚复用: `board_motor_pins.h` 里 USART1 的 `IOMUX` 写成 `GPIO_MUX_0`, 但 BSP 生成器 (git 6bbe9bd) 实际用 `GPIO_MUX_7` → 引脚复用选错 AF, 即使配置了也不工作.
4. 检查 finsh 源码: `shell.c / msh.c / msh_parse.c / cmd.c` 未纳入 CMake `RT-Thread_Nano_Src` 和 Keil .uvprojx 编译列表 → 宏开了也链接失败 (undefined reference to finsh_system_init).

**修复**:
- `finsh_config.h`: 开启 `RT_USING_FINSH`
- `rtconfig.h`: 开启 `RT_USING_CONSOLE`
- `board_motor_pins.h`: USART1 IOMUX `MUX_0` → `MUX_7`
- `board_init_at32m412.c`: 新增 `board_usart1_init()` (PB6/PB7 MUX_7 + 115200 8N1)
- `board.c`: `uart_init()` 改调 `board_usart1_init()`
- CMake + Keil: 纳入 finsh 4 个 .c 源文件
- 新建 `motor_shell.c`: 8 个 msh 命令 (pwm_info/pwm_duty/pwm_en/led/mc_state/fault/fault_clear/encoder)

**结果**: 编译链接通过, 但烧录后仍无输出.

### 第 2 轮: 串口初始化时序错误

**现象**: 第 1 轮修复后烧录, 串口仍完全静默.

**排查过程**:
梳理 RT-Thread 启动链路, 发现初始化顺序问题:
```
rt_hw_board_init()
  ├─ wk_system_clock_config()          ← 时钟 OK (180MHz)
  ├─ wk_periph_clock_config()          ← 已清空! 空操作!
  ├─ wk_nvic_config()                  ← 已清空! 空操作!
  ├─ rt_components_board_init()
  │    └─ uart_init() → board_usart1_init()  ← 此时 GPIOB/USART1 时钟未开!
  └─ SysTick_Config()

main()
  └─ motor_app_init()
       └─ board_clock_init()           ← 这里才开 GPIOB/USART1 时钟, 太晚了!
```

**根因**: `board_usart1_init()` 在 `rt_components_board_init` 阶段执行时, `CRM_USART1_PERIPH_CLOCK` 和 `CRM_GPIOB_PERIPH_CLOCK` 都没开 (它们在 `board_clock_init` 里才开, 而那要等到 main 线程的 `motor_app_init`). 往没开时钟的 USART1 寄存器写配置等于没写.

用户也指出 main.c 重复调用了 `clock_at32m412_init()` (与 `rt_hw_board_init` 里的 `wk_system_clock_config` 重复).

**修复**:
- `board.c` `rt_hw_board_init`: 把 `wk_periph_clock_config()`/`wk_nvic_config()` 替换为 `board_clock_init()`/`board_gpio_init()`/`board_nvic_init()` (在 `rt_components_board_init` 之前执行)
- `main.c`: 去掉重复的 `clock_at32m412_init()`
- `motor_app.c`: 去掉重复的 `board_clock_init/board_gpio_init/board_nvic_init` (已在 rt_hw_board_init 执行)

**结果**: 烧录后串口能打印 RT-Thread 版本横幅, 但没有 `msh />` 提示符, 无法输入.

### 第 3 轮: finsh 线程得不到调度

**现象**: 串口能打印版本横幅, 但没有 `msh />` 提示符, 无法输入命令.

**排查过程**:
版本横幅由 `rt_show_version()` 在 `rt_system_scheduler_start()` 之前打印 (不需要调度器). `msh />` 由 finsh 线程打印, 需要调度器启动后 finsh 线程被调度.

检查线程优先级:
- main 线程: 优先级 10 (RT_MAIN_THREAD_PRIORITY)
- finsh 线程: 优先级 21 (FINSH_THREAD_PRIORITY)
- 数值越大优先级越低

检查 `motor_app_run()`:
```c
void motor_app_run(void)
{
    while (1) {
        /* 空循环! 没有任何 rt_thread_mdelay / rt_thread_yield */
    }
}
```

**根因**: main 线程在 `motor_app_run` 的空 while(1) 里死循环, 不让出 CPU. 由于 main 线程优先级 (10) 高于 finsh 线程 (21), finsh 线程永远得不到调度, `msh />` 永远不出现.

**修复**: `motor_app_run()` while 循环加 `rt_thread_mdelay(10)`, 让 main 线程每 10ms 主动挂起, 给 finsh 线程调度机会.

**结果**: 烧录后出现 `msh />` 提示符, 所有 msh 命令可正常输入执行. `pwm_info` / `pwm_duty` / `pwm_en` / `mc_state` / `fault` / `led` 全部工作正常.

### 额外: LED 极性

**现象**: `led 1` 灭, `led 0` 亮, 与预期相反.

**根因**: 硬件 LED 负极接 IO, 低电平点亮. 程序里 `led 1` 执行 `gpio_bits_set` (高电平), 实际是灭.

**修复**: `motor_shell.c` led 命令反相 — `led 1` 执行 `gpio_bits_reset` (低电平=亮), `led 0` 执行 `gpio_bits_set` (高电平=灭). `board_gpio_init` 初始电平改为 set (灭). `board_motor_pins.h` 标注 LED 极性.

| msh 提示符 | (上电自动) | ✅ `msh />` 出现 |

### 踩坑总结 (后续避免)

1. **RT-Thread 初始化时序**: 板级硬件初始化 (时钟/GPIO) 必须在 `rt_components_board_init` 之前完成, 否则 INIT_BOARD_EXPORT 注册的设备初始化 (如 uart_init) 执行时硬件未就绪.
2. **main 线程 while 循环必须让出 CPU**: 否则所有低优先级线程 (finsh tshell 等) 饿死. 用 `rt_thread_mdelay` / `rt_thread_yield` / 等信号量.
3. **GPIO 复用编号查 BSP 生成器**: 手填 IOMUX 容易错, 以 Workbench 生成的 wk_*_init 里的 `gpio_pin_mux_config` 参数为准.
4. **ARMCC V5.06 默认 C90**: 不允许语句后声明变量 (GCC C11 允许). 跨编译器代码需用 C90 兼容写法 (变量声明在块开头).
5. **LED/继电器等外设极性**: 硬件接法决定 IO 电平语义 (低电平点亮 vs 高电平点亮), 代码需匹配, 头文件标注清楚.

## 2026-06-22 Stage 1 硬件 Bring-up (PWM 输出验证)

### 背景
Stage 0 基线重构完成后, Stage 1 实现最小集 TMR1 中心对齐 16kHz 3 路 PWM + 安全关断, 台架示波器验证波形.

### 关键决策: 系统时钟

spec §1.1 原标 96MHz, 但 `wk_system_clock_config` 实际配置 180MHz (PLL: 8MHz×90/(1×4)), 芯片 Flash 等待周期 5 支持 180MHz.

用户决定保持 180MHz (更强算力), 因此:
- `board_motor_pins.h`: `TMR1_CLOCK_HZ` = 180MHz, `TMR1_ARR` = 5624 (180e6/(2×16e3)-1)
- spec §1.1/§1.3/§1.4 时序常数同步更正为 180MHz

### 实现

- `board_init_at32m412.c`: 外设时钟 (GPIOA/B/TMR1/USART1/SCFG/PWC) + GPIO (nFAULT/LED/SPI2_CS/PWM_EN) + NVIC 优先级 (组4, TMR1_OVF=0/EXINT2=1/ADC=2/CAN=3/SysTick=14/PendSV=15, 仅设不使能)
- `motor_pwm_at32m412.c`: TMR1 中心对齐 TWO_WAY_3 + RCR=1 + ARR=5624 + 3路 PWM_MODE_A + CH4(ADC顶点触发预留) + brkdt禁用 + 50% 初始占空比
- `motor_app_init()`: 接入 board_init + motor_pwm_safe_init (MP6540H EN 保持低)

### 台架验证

示波器探 PA8/PA9/PA10, 确认 16kHz 中心对齐 50% 三相对齐波形. MP6540H_EN (PB10) 保持低 (禁用状态, 安全).

**结果**: ✅ PWM 波形正确, Stage 1 验收通过. (后通过 msh `pwm_info` 命令二次确认配置参数)

### RT-Thread 临界区发现

调研发现本工程 RT-Thread libcpu 的 `rt_hw_interrupt_disable` 用 PRIMASK (全局关中断), 非 BASEPRI. spec §3.5 原写的 `RT_KERNEL_BASEPRI` 不适用. Stage 1 不使能 TMR1_OVF 中断故无影响, FOC ISR 屏蔽风险留到 Stage 2/3 实测.

## Stage 2 Bug 修复: CCR=0 + kprintf %f - 2026-06-22

### 记录编号
S2-002

### 阶段
Stage 2 (调试修复)

### 目标
修复 mc_open 启动后 mc_debug 显示 CCR=0/0/0 的 bug, 以及 shell 浮点打印异常.

### 问题描述
1. **shell 浮点打印异常**: mc_debug 输出 `theta_e : %f rad (%f deg)`, mc_open 输出 `vd=%fV`, 所有 `%.2f`/`%.3f` 原样打印为字面 "%f"
2. **CCR=0**: mc_open 1000 60 启动后 (active=1, tick_count 递增), 但 CCR1/2/3 = 0/0/0, 电机不出力

### 根因分析
**问题 1**: RT-Thread Nano 的 `rt_kprintf` (kservice.c) 是最小化整数 printf, **不支持 %f**. 所有浮点格式串原样输出.
**问题 2**: ISR 诊断计数器定位到 `fault_hits` 持续递增而 `ol_hits=0`. 根因是 `motor_calibration_load()` 开机置位 `FAULT_CAL_INVALID` (0x40), 而 ISR 用 `fault_manager_any()` 检查"任意故障" → 把告警级 CAL_INVALID 当致命故障 → 走 fault 分支强制 50% 同电位 → CCR 看似为 0 (实际是 50% 但 s_dbg_ta 未写入).
- spec §4.7.3 明确: "FAULT_CAL_INVALID 不阻止电机使能, 但应作为告警"
- mc_open 检查的是 `motor_control.fault_flags` (实例自己的, =0), ISR 检查的是 `fault_manager` 的 `s_fault_flags` (=0x40), 两个故障系统不同步

### 处理措施
1. **%f 修复**: 所有 shell 浮点输出改为整数定点 (mV/mrad/mdeg/mrpm). mc_open 参数从 vd_volts (浮点V) 改为 vd_mv (整数毫伏). encoder 命令同步改.
2. **故障分级修复**:
   - `fault_manager.h` 新增 `FAULT_FATAL_MASK` = DRIVER|OVERCURRENT|SENSOR|UNDERVOLTAGE|OVERVOLTAGE (不含 CAL_INVALID/CAN_TIMEOUT)
   - 新增 `fault_manager_any_fatal()`: 仅致命位
   - ISR 故障分支改用 `fault_manager_any_fatal()` (非 `any()`)
   - mc_open 启动检查改用 `fault_manager_any_fatal()` (与 ISR 一致)
3. **ISR 诊断计数器**: mc_debug 新增 `ol_branch_hits`/`fault_hits`/`disabled_hits`, 用于定位 ISR 走哪个分支

### 验证方法
通过 COM9 (JLink CDC UART) 逐字符发送命令 (适配 finsh 轮询 getchar), 验证:
```
mc_open 1000 60
mc_debug  -> ol_hits=32647 递增, fault=0, CCR=3186/2643/2437
mc_debug  -> theta=518mrad, valpha=786mV, vbeta=495mV (正弦变化)
```
数学验证: √(918²+253²)≈952mV ≈ vd=1000mV ✓; CCR 均值≈2755 ≈ 2812(50%) ✓; m=1/12=0.083, CCR 波动±375 ≈ 2812×0.083 ✓

### 关键发现 (finsh 串口限制)
- `rt_hw_console_getchar()` (board.c) 是**轮询**读 USART, 无 RX 中断/FIFO. 一次性发送整行会 overrun 丢字符 (只回显首字符).
- 自动化测试必须**逐字符发送 + 等待回显**, 模拟人工输入. tests/com9_test.py 已实现此模式.

### 关键 Bug 定位与修复

#### Bug 1: 板子无法启动 (ADC 校准挂死)
- **现象**: 烧录后串口无 msh 提示符, 板子不启动
- **根因**: `current_sense_at32m412_init()` 只开了 `CRM_ADC1_PERIPH_CLOCK`, 未开 `CRM_ADC2_PERIPH_CLOCK`. AT32M412 的 ADC1/ADC2 有独立时钟使能位, 但 ADC common 配置需 ADC1 时钟. 仅开 ADC1 时, ADC2 使能后校准 while 循环永久挂起 (adc_flag_get(ADC_RDY_FLAG) 永远 RESET)
- **修复**: 同时开 `CRM_ADC1_PERIPH_CLOCK` + `CRM_ADC2_PERIPH_CLOCK`. 另外给所有 ADC 校准 while 循环加超时保护 (100000 次循环), 防硬件异常时挂死

#### Bug 2: ADC 注入序列返回全 0
- **现象**: mc_current 显示 ia=0 ib=0 ic=0 (raw 全 0), 零偏标定失败 (offset=0)
- **根因**: TMR1 CH4 仅调用 `tmr_channel_value_set(TMR1, CH4, ARR)` 设比较值, 未调用 `tmr_output_channel_config(TMR1, CH4, ...)` 配置为输出比较通道. CH4 不产生比较事件, ADC 注入序列无法被 TMR1_CH4 触发, 注入数据寄存器保持 0
- **验证**: 对照参考工程 mc_hwio.c line 226/1313, 参考工程对 ADC_TIMER 的 CH4 调用了 `tmr_output_channel_config`
- **修复**: `motor_pwm_at32m412_init()` 中 CH4 增加 `tmr_output_channel_config` + `tmr_output_channel_buffer_enable`

#### Bug 3: ADC 采样点错误（2026-07-21 已更正）
- **当时现象**: CH4 配置正确后, ADC raw 全部接近 2048 (V_REF), 即使电机旋转电流也不变化。
- **当时误判**: 2026-06-22 曾错误地把 SOx 解释为另一桥臂导通有效，并把 CH4 从 ARR 改到谷底 1。该解释已被后续占空比扫描、全象限闭环和 MP6540H 低边电流检测语义否定，不应再作为采样设计依据。

- **修复**: 窗口放宽到 50 LSB (≈0.16A), 在安全范围内

#### Bug 5: 标定时 MP6540H 未使能
- **现象**: mc_cal 标定 a=1643 (偏差 405 LSB), b/c 接近 2048

## Stage 5 调试: PA7 (SOC) ADC 读数异常 — 芯片引脚硬件损坏 - 2026-06-24

### 记录编号
S5-DBG-001

### 调试目标
排查 ADC2 注入序列中 SOC (PA7/ADC2_IN7) 读数恒为 ~0x000F (接近 0), 而 SOA (PB1/CH9)、SOB (PB0/CH8) 正常 (~2048) 的原因。

### 现象
- Keil 调试器寄存器界面: SOA/SOB 注入数据 ~2048 (正常零电流), SOC ~0x000F 波动 (异常)
- PA7 引脚外部实测电压 ~1.65V (MP6540H SOC 输出, 应读 ~2048)
- 硬件已排查: 焊接无问题, 端口电压 1.7V 正常
- SOA/SOB 同板同芯片正常 → 排除芯片整体故障

### 排查过程 (systematic-debugging)

#### Phase 1: 证据收集
1. **代码配置确认** (`current_sense_at32m412.c` / `board_motor_pins.h`):
   - SOA=PB1/ADC2_CH9, SOB=PB0/ADC2_CH8, SOC=PA7/ADC2_CH7
   - 三相 GPIO 均配 `GPIO_MODE_ANALOG` + `GPIO_PULL_NONE`, 无 mux (ANALOG 模式不需要)
   - board_gpio_init 只配 PA0(LED)/PA15(CS), 未碰 PA7
   - ADC2 注入序列顺序 SOA→SOB→SOC, TMR1_CH4 触发

2. **PA7 复用功能查证** (DS_AT32M412_416 V2.02, page 25):

   | 模式 | PA7 复用功能 |
   |---|---|
   | ANALOG | ADC2_IN7 / CMP2_INP0 / OP1_INP2 / OP2_INP0 |
   | 默认 | **OP2_OUT** (运放2输出) |
   | MUX_1 | TMR1_CH1C (互补) / TMR3_CH2 / TMR11_CH1 |
   | MUX_5 | SPI1_MOSI / I2S1_SD |
   | MUX_4 | I2C2_SCL / CMP2_OUT |

   **PA7 是 OPAMP2 的输出引脚**。PB0/PB1 的复用功能里**没有 OPAMP 输出**, 这解释了为何只有 SOC 异常。

3. **OPAMP 默认状态查证** (RM_AT32M412_416, §21 运算放大器):
   - `OPx_CTRL.OPEN` 复位值 = 0x0 (运放默认禁用)
   - `OPx_CTRL.OPOUTSEL` 复位值 = 0x0 = "OP 输出到 GPIO 上" (即使 OPAMP 禁用, 输出端仍连 GPIO)

#### Phase 2: 假设与验证

**假设 A (被证伪): OPAMP2 输出占用 PA7**
- 设 `OP2_CTRL.OPOUTSEL=1` (OP 输出重定向内部 ADC, 释放 GPIO)
- `OP2_BASE = 0x40013B04` (at32m412_416.h: APB2PERIPH_BASE + 0x3B04)
- 写入后读回: `OP2_CTRL before: 0x00000000`, `OP2_CTRL after: 0x00000100` (bit8=1 确认写入生效)
- **结果: PA7 仍 1.65V, ADC 仍异常** → 假设 A 推翻
- 注: OPAMP 禁用时 (OPEN=0) 输出级本就无驱动能力, OPOUTSEL 对禁用 OPAMP 影响有限, 故与本次故障无关

**假设 B (排除): TMR1_CH1C 互补通道驱动 PA7**
- 查 `motor_pwm_at32m412.c`: `occ_output_state = FALSE` (明确禁用互补), 只配 CH1/2/3/4
- TMR1 GPIO mux 只配 PWMA/B/C (PA8/9/10), 未碰 PA7
- → 排除

**假设 C (排除): CMP2 比较器影响**
- PA7 = CMP2_INP0 (输入, 高阻), CMP2_OUT 输出需 MUX_4 (本工程未设)
- → 排除

**假设 D (确认): 芯片 PA7 硬件损坏**
- 决定性验证: OPAMP 已断开 (OPOUTSEL=1 读回确认) + PA7 配推挽输出置 0
- 对照组 PA0 同样推挽置 0 → **PA0 = 0V** (测试方法有效)
- **PA7 仍 1.65V** (推挽输出无法驱动)
- 1.65V ≈ VREF/2 (3.3V/2), 是损坏引脚内部固定电平的典型特征

### 结论

**根因: AT32M412 芯片 PA7 引脚硬件损坏。**

在 OPAMP2 输出已断开 (OPOUTSEL=1 读回确认)、TMR1_CH1C 未配置、CMP2 未激活的情况下, PA7 配推挽输出置 0 仍稳在 1.65V (= VREF/2), 只剩芯片引脚硬件损坏一个解释。PB0/PB1 同板正常, 排除芯片整体故障, 为 PA7 单引脚问题。

**OPOUTSEL 与本次故障无关**: OPAMP2 默认禁用 (OPEN=0), 输出级无驱动能力, 不构成"冲突致伤"条件。设 OPOUTSEL=1 既不是根因也不是必要预防措施。

### 致伤原因
未明。可能因素: ESD、焊接热损伤、引脚瞬时过压、出厂缺陷。无证据指向具体原因。

### 处理措施
1. **换芯片验证**: 换一片 AT32M412, 烧同样固件, PA7 若恢复 ~2048 → 实锤该芯片 PA7 损坏。这是最终确认, 也是解决方案。
2. **临时绕过 (若急用)**: 无法绕过。MP6540H 三相电流采样缺一相即无法做完整 FOC, 软件估算 ic=-ia-ib 不含 C 相真实信息, 只适合无负载验证。

### 验证方法
- 软件验证 OPAMP 断开: `*(volatile uint32_t*)0x40013B04 = (1u<<8)`, 读回 0x100
- 推挽对照测试: PA0 推挽置 0 → 0V (正常), PA7 推挽置 0 → 1.65V (异常)
- 换片确认: 新芯片 PA7 ADC 读数 ~2048

### 换片后实测结果 (2026-06-26 追加)

换了芯片后, 烧录电机驱动固件**第一次上电 PA7 仍异常**。随后用 AT32M412 标准库 GPIO 例程测试 PA7 IO 反转, 万用表测得电平能正常翻转。之后再烧回电机驱动固件, **ADC 读数恢复正常**。

### 暂时结论 (待第二块板验证)

**换芯片后 PA7 恢复正常**, 但恢复过程出现两个未完全解释的现象:
1. 换片后第一次烧电机固件仍异常
2. 跑一遍 GPIO 例程 (IO 反转) 后, 再烧电机固件才正常

可能的解释 (未证实): 某种引脚/外设状态的"残留"——首次上电时 PA7 的模拟外设 (OPAMP/CMP) 或 GPIO 配置处于非预期状态, GPIO 例程对 PA7 做了完整的数字 IO 配置 (含 mux/clear), 相当于一次"复位清扫", 之后电机固件再配置 ANALOG+ADC 才生效。也可能旧片确实损坏、新片只是首次配置时序巧合。

**判定为芯片问题的依据尚不充分**。旧片推挽置 0 仍 1.65V 是硬证据指向损坏; 但新片"换片即好"被 GPIO 例程这个中间步骤搅动, 不能 100% 排除"配置残留"类根因。**待焊接第二块板时复测**: 若第二块板首次烧电机固件即正常 → 旧片损坏实锤; 若第二块板也复现"首次异常、跑 GPIO 例程后正常" → 根因倾向配置残留, 需排查 init 时序。

### 关键参考资料
- 数据手册: `DS_AT32M412_416_V2.02_CH.pdf` page 25 (PA7 复用功能表)
- 用户手册: `RM_AT32M412_416_CH_V2.01.pdf` §21 (OPAMP), page 400-401 (OPEN/OPOUTSEL 寄存器位)
- 寄存器地址: `at32m412_416.h` OP2_BASE = APB2PERIPH_BASE + 0x3B04

### 踩坑总结
1. **PA7 是 AT32M412 的特殊引脚**: 默认连 OPAMP2 输出 (OP2_OUT), ANALOG 模式下同时连 ADC2_IN7/CMP2/OPAMP 多个模拟外设。排查 ADC 异常时必须先查数据手册复用功能表, 不能假定普通 ADC 引脚。
2. **OPAMP 禁用 ≠ 输出端断开**: OPEN=0 (运放禁用) 时 OPOUTSEL 仍控制输出端是否连 GPIO。但禁用 OPAMP 输出级无驱动能力, 实测对本故障无影响。
3. **推挽对照测试是判芯片损坏的有效方法**: 同板选一个已知正常引脚 (如 PA0) 做同样配置对照, 排除软件配置问题, 单引脚异常即指向硬件。
4. **VREF/2 电平是损坏引脚特征**: 引脚内部通路断开/短路时, 常稳在半电源电平。
5. **"换片即好"需谨慎归因**: 若换片后恢复过程中跑了其他固件 (如 GPIO 例程), 不能简单归因芯片损坏。需用全新板/全新片首次只烧目标固件来排除配置残留。

## finsh 方向键显示 [A [B [C [D — getchar 返回类型 bug - 2026-06-26

### 记录编号
S5-DBG-002

### 阶段
Stage 5 电流环台架验收调试期间

### 现象
串口终端 (putty/SSCOM) 按上下左右方向键, 屏幕显示 `[A [B [C [D` 字符, 不能切换历史命令, 不能移动光标。

### 根因
`rt_hw_console_getchar` (board.c) 声明返回 `char`, 内部调用 `board_usart1_rx_dma_getchar()` (返回 `int`, -1 = 无数据)。

```
board_usart1_rx_dma_getchar() 返回 int: -1 (0xFFFFFFFF)
    ↓ char 截断
rt_hw_console_getchar 返回 char: 0xFF
    ↓ 隐式提升回 int
finsh_getchar 返回 int: 0x000000FF = 255
    ↓ shell.c:488
if (ch < 0)  →  255 > 0, 检查失败, 不 continue
    ↓
255 被当有效字符塞进方向键 ESC 序列中间
```

方向键序列是 `ESC(0x1b) → [(0x5b) → A/B/C/D(0x41-44)` 三字节状态机 (shell.c:500-517):
1. 收到 `0x1b` → `shell->stat = WAIT_SPEC_KEY`
2. 收到 `0x5b` → `shell->stat = WAIT_FUNC_KEY`
3. 收到 `0x41-44` → 执行方向键动作

ESC 和 `[` 之间如果 DMA buffer 暂时无数据, `getchar` 返回 `-1`, 经 `char` 截断变 `255`, shell 把 255 当有效字符处理 → 状态机从 `WAIT_SPEC_KEY` 回到 `WAIT_NORMAL` (0xFF != 0x5b) → 后续的 `[` 和 `A/B/C/D` 被当普通字符回显。

### 修复
- `project/src/board.c`: `rt_hw_console_getchar` 返回类型 `char` → `int`, 直接 return `board_usart1_rx_dma_getchar()` (不再截断)
- `middlewares/rt-thread/components/finsh/shell.c`: `extern char rt_hw_console_getchar(void)` → `extern int rt_hw_console_getchar(void)`

### 验证
烧录后串口终端按方向键正常: 上/下切换历史命令, 左/右移动光标, 不再显示 `[A [B [C [D`。

### 教训
- **char 返回值不能区分 -1 和 0xFF**: getchar 类函数 (需用 -1 表示无数据) 必须返回 int, 不能用 char。这是 C 语言经典陷阱, char 隐式转换 int 时符号扩展/截断会丢失 -1 语义。
- **DMA 改造引入的回归**: 原 polling getchar 直接读 USART1->dt, 无数据时返回 -1 也是 char 截断 (但 polling 模式下不会在 ESC 序列中间返回 -1, 因为有字符才读)。DMA 环形 buffer 模式下 getchar 在任意时刻都可能返回 -1 (buffer 空), char 截断的 -1 变 255 破坏了方向键状态机。

### 记录编号

- 开环拖动模式，theta 从 6.01 rad 下降到 0 的过程中，foc_sin_f 返回值持续为 0
- 波形在 theta ≈ 6.01 rad 处出现"跳崖"式不连续，理论上 sin 应是平滑过渡

### 根因分析

#### 代码定位
查表函数 `foc_sin_f()` 的执行路径：

```
theta ≈ 6.01 rad → norm = fmodf(theta, 2π) ≈ 6.01
fidx = norm × 256 / 2π ≈ 6.01 × 40.7437 ≈ 244.87
idx0 = (uint32_t)244.87 = 244
idx1 = (idx0 + 1) & 0xFF = 245
frac = 0.87

v0 = s_sin_table[244] = ?
v1 = s_sin_table[245] = ?
```

#### 直接原因
s_sin_table 数组声明为 `static const float s_sin_table[TRIG_TABLE_SIZE]` 即 `[256]`，但初始化列表**只提供了 244 个**浮点数字面量（检查 `foc_core.c` 第 25-57 行的初始化器列表，实际元素数仅 244）。

C 标准（C90 §6.5.7 / C99 §6.7.8）规定：
> 如果初始化器提供的值少于数组元素个数，剩余元素被**隐式零填充**。

因此：
- `s_sin_table[0..243]` = 提供的值（部分也存在精度不足的问题，但至少非零）
- **`s_sin_table[244..255]` = 0.0f** ← 这就是 sin 为 0 的根因

正常第 245 元素（索引 244）应为 `sin(2π × 244/256) = sin(5.9855) ≈ -0.195090`，实际为 0.0。

### 根本原因
**Agent / AI 工具盲目生成代码**：设计规格明确要求 256 点查表（`TRIG_TABLE_SIZE = 256`），但自动生成的初始化列表只生成了 244 个值就被截断。开发者未对生成的查表数组做长度校验，编译也未报错（C 标准允许部分初始化），导致这个"静默截断"缺陷被带入固件。

### 引发的连锁调试成本
这个隐蔽的 bug 导致了一系列后续误导性的调试投入：
1. **怀疑 sin 查表函数的归一化/插值算法** → 审查 `foc_sin_f` 的 `fmodf`、线性插值逻辑 → 无问题
2. **怀疑 theta 角度的生成逻辑**（开环斜坡、编码器读取） → 审查角度更新路径 → 无问题
3. **怀疑编译器优化导致查表异常** → 添加 `volatile`、调试快照 → 仍异常
4. **新增串口调试输出**（sin/cos Q15 写入 `mc_debug`） → 最终暴露 sin 值为 0

**这些排查原本都可以避免**，如果生成代码后做一项简单的检查：确认初始化列表的元素数量等于数组声明长度。

### 修复

**根因修复**：`foc_core.c` s_sin_table 补全为完整的 256 点正确值（第 245 项以后不再为零填充）。

**连带改动**：
- `motor_control_isr.c`: s_sin / s_cos 加 `volatile` + 添加调试快照变量，防止调试器优化
- `motor_control_isr.h`: 调试结构体增加 sin_q15 / cos_q15 字段，通过 `mc_debug` 命令可见
- `motor_shell.c`: `mc_debug` 增加 sin/cos Q15 定点值显示，便于串口观测

### 处理措施
1. 重新生成完整的 256 点 sin 表（使用 Python/C 生成脚本，保证数学正确性）
2. 逐项核对确认 256 个值完整无缺
3. lib 层增加编译期断言，确保查表数组长度与 TRIG_TABLE_SIZE 一致：
   ```c
   STATIC_ASSERT(sizeof(s_sin_table) / sizeof(s_sin_table[0]) == TRIG_TABLE_SIZE);
   ```
4. 所有未来自动生成的数组初始化列表，必须附加"元素计数校验"步骤

### 验证方法
- 编译通过（无 zero-fill 告警）
- `mc_debug` 输出 sin_q15 在 theta 全范围非零且连续变化
- 示波器查看开环拖动模式下三相 PWM 波形连续无跳变

### 结论
**罪魁祸首：Agent 生成的 sin 表只有 244 个元素，C 标准零填充了剩余的 12 个元素为 0.0**。这是一个"生成的代码静默出错、编译不报错、运行才暴露"的典型 AI 生成代码陷阱。

### 踩坑总结
1. **数组初始化列表必须计数校验**：任何时候声明一个固定大小的数组并用初始化列表填充，都应验证元素数是否等于数组长度。C 编译器对这种"少填"行为零报错（合法语法），后果只能运行时暴露。**建议在自动生成代码后立即加 `static_assert` 或元素计数检查**。
2. **AI 工具的数字细节需人工复核**：Agent 可在高层逻辑（算法框架、接口设计）上表现优秀，但在精确数据生成（如 256 个浮点数序列）上容易截断/遗漏。此类任务应:
   - 使用脚本生成数据（Python 生成 256 点→C 数组格式→`#include` 或 `xxd` 嵌入）
   - 或用 `static_assert` 编译期保护
3. **零填充是 C 静默陷阱**：`int arr[100] = {1,2,3};` 编译通过、链接通过、零 warning，但 arr[3..99]=0。如果业务逻辑依赖完整初始化，这就是定时炸弹。查表类数组尤其致命。
4. **调试路径的误导性**：问题表象在 sin 值突变为 0 → 自然怀疑算法/角度/优化 → 每条路排查一圈后才回到数据本身。如果最初有编译期长度断言，整个调试链条可以缩短到 0。

- `raw16` 是机械角，范围 0..65535，对应机械一圈。
- `s_snapshot.elec_mrad` 是电角度，范围 0..6283 mrad。

```c
corrected = encoder_apply_calibration(raw);
mech_diff = (uint16_t)(corrected - s_zero_raw);
theta = ((float)mech_diff * (float)MOTOR_POLE_PAIRS * TWO_PI_F) / 65536.0f;
```

因此 raw16 一个机械周期对应 `elec_mrad` 约 7 个锯齿周期是正确现象，不应期待 1:1 周期。

注意：`s_snapshot.mech_mdeg` 不是电角度，它只是未校正 raw 机械角转换成的机械毫度：

```c
s_snapshot.mech_mdeg = raw * 360000 / 65536;
```

后续如果需要更直观地在示波/调试器中观察电角度，可增加一个 `elec_u16` 调试量：

```c
elec_u16 = ((uint32_t)(corrected_raw - zero_raw) * MOTOR_POLE_PAIRS) & 0xFFFF;
```

这样可用 0..65535 的同尺度波形直接对比 raw 机械角与电角度周期关系。

## 2026-07-10 编码器速度估计波动调试

### 现象
编码器标定后角度数据目前看已经正常，但在开环拖动时，理论上电机速度应当比较均匀，调试输出中的速度量仍有明显波动。

本轮使用 J-Link 和串口 COM9 联调，重点确认两个问题：

1. 当前编码器角度读取频率是多少。
2. 速度估计到底是角度真的在抖，还是估计算法把量化噪声放大了。

### 当前代码逻辑
当前编码器采样路径为：

```text
TMR7_GLOBAL_IRQHandler
  -> encoder_service_acquire_once()
```

`encoder_service_acquire_once()` 由 TMR7 中断驱动，当前采样频率为 4kHz。

FOC 控制中断为 16kHz。也就是说，FOC 每 4 次中断才会拿到一次新的编码器角度样本。

原来的 `encoder_tracker` 逻辑更像一个简化 PLL/PI 跟踪器：

```text
encoder_tracker_update_sample(angle)
  -> 用角度误差更新 speed_est

encoder_tracker_tick()
  -> 每个 FOC tick 用 speed_est 外推 angle_est
```

这个逻辑可以做角度外推，但速度量对单点角度误差、采样相位和启停状态比较敏感。调试中还看到停止/重新启动后 tracker 速度可能保留上一段状态，因此开环拖动时速度波形会显得比实际更乱。

另外，`s_snapshot.speed_raw` 这个量也不能直接作为当前速度判断依据：运行采样路径主要读取角度，raw frame 中的速度字段并不总是同步更新，实测时它经常为 0。

### 调试判断
单次 raw 差分本身会有量化噪声：

```text
raw_delta = raw_now - raw_prev
```

在 4kHz 采样下，低速时每个采样周期只跨过少量 raw LSB，单点差分会把编码器量化、SPI 采样相位、校正表局部斜率都直接映射成速度抖动。

所以这次倾向于把速度估计从“单点/PLL 误差驱动”改成“校正后角度的固定窗口差分”：

```text
1. 每次 4kHz 编码器采样时，先得到 corrected_raw16。
2. 对 corrected_raw16 做 unwrap，得到连续机械角 corrected_unwrapped。
3. 保存最近 N 个样本。
4. 用 corrected_unwrapped[n] - corrected_unwrapped[n-N] 计算窗口平均速度。
5. 输出机械速度和电速度：

   speed_mech = delta_raw * 2pi / 65536 / (N * Ts)
   speed_elec = speed_mech * pole_pairs
```

当前准备使用 `N=32`，在 4kHz 下窗口约 8ms。这个窗口比单点差分平滑很多，但延迟仍在速度环可以接受的范围内。

## 2026-07-10 电流环补测与保护误触发排查

### 背景
准备测试 Stage 6 速度环时发现 `mc_speed` 很快进入故障，进一步确认前面的电流环还没有形成完整台架验收结论，因此暂停速度环，先回到 Stage 5 电流环补测。

### 先遇到的保护误触发
测试 `mc_speed 60`、`mc_speed 10` 和 `mc_cur 50 enc` 时，多次出现：

```text
fault = 0x00000008
  UNDERVOLTAGE
```

但同一时间 `mc_debug` 和 `vbus` 看到的 VBUS 都在 12.1V 左右：

```text
vbus : 12118..12152 mV
```

排查代码后确认，FOC ISR 内每 1ms 软件触发一次 ADC2 ordinary conversion 读取 VBUS，而 ADC2 同时承担 TMR1_CH4 触发的注入电流采样。普通转换在 ISR 内会和注入序列冲突，出现超时或低值假样本，随后被欠压保护锁存。

处理措施：

1. 对 VBUS 欠压/过压先尝试加连续样本 debounce，但仍会误触发。
2. 最终把 VBUS ordinary ADC 软件触发从 FOC ISR 移除。
3. ISR 内暂时使用 `VBUS_FALLBACK_V=12V` 缓存参与 SVPWM 计算。
4. `vbus` shell 命令仍可人工读取母线电压。

这个处理让电流环测试不再被 VBUS 误故障打断，但也意味着运行时 VBUS 保护需要后续单独设计到低频线程或更可靠的硬件触发路径，不能长期停留在这个临时方案。

另一个保护误触发点是相过流单拍锁存。测试中曾出现 `iq_ref` 很小但 `OVERCURRENT` 被锁住的情况，快照电流并不大。现已给相过流增加短 debounce：

```text
OVERCURRENT_DEBOUNCE_TICKS = 4
```

也就是 16kHz 下约 0.25ms。真实持续过流仍能快速保护，单拍 ADC 毛刺不会立即锁死。

### 2026-07-10 追加：电流采样触发点修复

在继续排查 `mc_cur` 不跟随目标的问题时，新增了 `cur_avg` 诊断量：

```text
cur_avg : id=<mA> iq=<mA> window=256
```

窗口为 256 个 FOC tick，约 16ms。复测发现默认 CH4=1 时，`iq_avg` 基本贴近 0mA，不随 `iq_ref=+/-50/100/200mA` 变化；但 PI 输出电压和 PWM duty 已经明显变化。这说明问题不是 `mc_debug` 单点快照抖动，而是电流反馈在默认采样点没有读到有效相电流。

随后用新增命令扫描 ADC 注入触发点：

```text
pwm_adc_trig <ticks>
```

ALIGN 固定电压下的结论：

- CH4=1..2000：三相电流基本只在零点附近跳动，随 ALIGN 电压不明显增加。
- CH4=2500..3000：开始读到明显电流响应。
- CH4=4000 以后：读数有较大固定偏置，Park 后 Id/Iq 容易进入错误象限。

进一步用 `CH4=2500` 做 enc 电流环复测：

```text
iq_ref=  50mA -> iq_avg ~=   51mA
iq_ref= 100mA -> iq_avg ~=   97mA
iq_ref= 200mA -> iq_avg ~=  199mA
iq_ref= -50mA -> iq_avg ~=  -49mA
```

因此将默认 ADC 触发点从谷底 `1` 改为 `2500` ticks，并保留 `pwm_adc_trig` 作为后续台架/示波器微调接口。`pwm_info` 当前应显示：

```text
CCR4 : 2500 (ADC trigger)
```

本次修复后，正向低电流和小负向电流已能闭环跟随；但 `-100mA/-200mA enc` 仍会跑到约 `id_avg=850mA, iq_avg=320mA` 的异常工作点。当时误将 MP6540H 低边导通窗口采样判断为“高边电流镜”，因此把异常归因于负向较大电流/不同 PWM 象限下的采样窗口或重构策略；该判断已在 2026-07-21 的极性实测中更正，实际根因是器件电流方向与 FOC 相电流约定相反。

当前建议：

```text
1. Stage 6 速度环先只按正向低速/低电流做受控验证。
2. 负向速度环或双向力矩控制前，继续处理负向较大 Iq 的采样/重构问题。
3. 保留 cur_avg 和 pwm_adc_trig，后续配合示波器确认 SOA/SOB/SOC 有效窗口。
```
